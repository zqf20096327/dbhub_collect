### 怎样避免提速后仍得 0 分？

**本题评的是质量合格前提下的端到端提速，kernel 更快不等于一定有分。** 先区分两种情况：完成检查但硬门槛未通过，本次总分为 0；仓库、版本、编译或运行错误导致未完成评测，本次不计分，见下一问。

目前 **247 个门槛零分提交**的失败分布如下。本表不包含下一问的提交与执行错误，各行互斥，可直接相加。

| 门槛零分原因 | 提交数 | 占 247 个门槛零分 |
| --- | ---: | ---: |
| 只有正式 Recall 门槛未通过 | 125 | 50.6% |
| 正式 Recall 与显存、性能等其他门槛同时未通过 | 39 | 15.8% |
| Quick Recall 低于 0.75 | 14 | 5.7% |
| 其他门槛未通过，未记录 Recall 失败 | 69 | 27.9% |
| **合计** | **247** | **100.0%** |

**178 个零分提交涉及 Recall 不达标，占 72.1%。** 另外，显存相对上限失败涉及 58 个（23.5%），查询性能回归涉及 32 个（13.0%）；这些检查项可能与 Recall 或彼此重叠，不能再与上表相加。Quick 未通过时，后续正式门槛可能尚未执行。

这里的“精度问题”指 **Recall／检索质量不达标**。图质量、搜索参数、ID 映射、持久化与重载、内部数值计算等都可能影响 Recall，应以自测证据定位。

#### 目前怎样评分？

1. **先过全部硬门槛，再算性能分。** 总分为 20 分：硬门槛 4 分、构建性能 14 分、查询性能 2 分。全部硬门槛通过才获得 4 分并计算性能分；任一硬门槛失败，总分为 0，不能用速度补偿质量、资源或查询回归。
2. **正式 Recall 同时检查绝对下限和同轮基线差。** 对每一组结果，候选 Recall 必须满足 `candidate >= max(绝对下限, 同轮 baseline - 0.005)`。`0.005` 等于 **0.5 个百分点**，不是相对下降 0.5%。四组分别检查，不能加权平均后抵消失败。

| 正式检查组 | 绝对 Recall 下限 | 实际通过线 |
| --- | ---: | --- |
| SIFT250K / Top-10 | 0.95 | `max(0.95, 同组 baseline - 0.005)` |
| SIFT250K / Top-100 | 0.95 | `max(0.95, 同组 baseline - 0.005)` |
| Hidden250K / Top-10 | 0.90 | `max(0.90, 同组 baseline - 0.005)` |
| Hidden250K / Top-100 | 0.85 | `max(0.85, 同组 baseline - 0.005)` |

例如 Hidden Recall@100 的同轮 baseline 为 91.4243%，候选至少要达到 **90.9243%**；即使候选达到 90.5959%、高于 85% 绝对下限，仍会因为比基线下降超过 0.5 个百分点而得 0 分。正式 Recall 失败的 164 个提交中，115 个未触发绝对下限，却触发了相对基线差门槛；另 49 个同时触发两项。按检查组看，这 164 个提交中有 162 个涉及 Hidden Recall@100 的相对基线差失败。该示例不是 Hidden 的固定通过线，正式判定始终使用本任务同轮 baseline。

3. **Quick 通过不代表正式质量通过。** Quick 使用最多 10K 条 SIFT，Top-10、Top-100 的 Recall 均须至少为 0.75。正式评测使用两个 250K 数据集、`nq=4096` 的四组结果；正式 `nq=1` 只作诊断，不参与正式 Recall 与查询性能评分，但第一条合法查询的耗时计入构建时间。
4. **资源与查询回归是独立门槛。** 显存峰值既不能超过 45 GB，也不能超过同轮 baseline 的 1.25 倍；评测进程内存不超过 96 GB，整轮 GPU 评测上限 15 分钟。每个正式数据集的 Top-10、Top-100 查询 QPS 比取几何平均后，须至少达到同轮 baseline 的 90%，另一数据集更快不能抵消回归。
5. **比较的是同轮冻结 V5 基线，不是 CPU 或自选旧版本。** 构建计时覆盖冷 DDL 建索引至第一条固定查询完成，不只计 GPU kernel；原始数据导入、服务启动和源码编译不计入构建性能。SIFT 与 Hidden 的性能权重为 40%／60%，用加权几何平均计算综合加速比，构建 3.0 倍、查询 1.5 倍分别达到满分。

设综合构建加速比为 $B$、综合查询加速比为 $Q$，`clamp(x, 0, 1)` 表示把结果限制在 0～1：

$$
B=B_{\mathrm{SIFT}}^{0.4}B_{\mathrm{Hidden}}^{0.6},\qquad
Q=Q_{\mathrm{SIFT}}^{0.4}Q_{\mathrm{Hidden}}^{0.6}
$$

$$
\text{总分}=4+14\,\min\left(1,\max\left(0,\frac{\ln B}{\ln 3.0}\right)\right)
+2\,\min\left(1,\max\left(0,\frac{\ln Q}{\ln 1.5}\right)\right)
\quad\text{（仅当全部硬门槛通过）}
$$

每个数据集的查询加速比是 Top-10、Top-100 两个 QPS 比的几何平均。性能分按对数连续增长，并非线性增长；某项综合加速比不超过 1.0 时，该项性能分为 0，但全部硬门槛通过仍有 4 分。

#### 提交前按什么顺序自测？

1. 先验证仓库、版本与统一离线编译，再验证完整 SQL 建索引和查询路径；不能用预编译产物或独立 kernel 测试代替。
2. 在相同数据、设备、环境、SQL 和冷启动条件下，配对运行冻结 V5 基线与候选；检查每条查询返回恰好 `k` 个合法、互不重复的 ID，并逐组记录 Recall、基线差和通过线。
3. 覆盖 GPU 预热、小规模、正式规模和不同维度。内部 FP16／混合精度优化应验证距离累计、溢出、图边与重载后的结果；保持外部 FP32 输入并不自动保证内部数值稳健。
4. 再检查显存的两条上限、主机内存和每个数据集的查询回归，最后逐步提速。一次只改一类策略，保存 commit、参数、质量与资源记录，留出自测余量，不靠反复提测碰边界。

Hidden 数据、顺序与 ID 不公开。合法的 256 维自测数据只能用于开发验证，不能保证 Hidden 通过，也不需要获取隐藏答案。真实 GPU 建图、固定 hipVS/cuVS CAGRA 搜索后端、结果完整性及原有 CPU VSAG 基本功能等义务仍须遵守。内部混合精度允许探索，但不能改变对外 FP32/L2 语义或绕过 GPU 图检索。

平台若只显示 `failMsg`，不要把执行错误码当成 Recall 门槛原因；门槛失败原因随子题结果回传（`testCaseResult` 中的 `message`）。页面未展示时，请向组织方提供任务 ID 请求核对，不要公开凭据，也不必为了查看历史原因重复提测。

| --- | --- | ---: |
| 编译 | 编译提交代码、链接并校验产物 | 约 2 分 40 秒 |
| 测评执行 | 正确性检查、性能测试及必要的环境准备与清理 | 约 7 分钟 |

### 为什么实际可用时长少于发放预期？

平台最低计费规则可能使短时多次启动、释放或重新创建实例更快耗尽额度。单个实例最长运行 4 小时，不代表额度一定可连续使用 4 小时。建议提前准备任务，减少反复启动并留意余额与扣费记录。

### 实例快到期了，但任务还没完成，怎么办？

本赛事远程容器为非持久化开发环境，释放或自动回收后，新增或修改的文件不会保留。

建议将代码保存在本地，按需上传至远端运行；在远端开发时，定期将代码、数据、检查点和运行结果同步回本地。手动释放或自动回收前，务必完成备份，并确认重要文件已成功保存。

SSH 连接本身不会自动映射或同步文件，·请勿将重要文件仅保存在远端容器中。
