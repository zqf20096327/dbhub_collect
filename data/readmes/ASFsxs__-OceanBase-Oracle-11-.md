## 🎯 第一站：思维重构——从集中式到分布式的认知跃迁

对于熟悉传统 Oracle 的开发者来说，学习 OceanBase 的第一步不是掌握新语法，而是理解一套全新的架构哲学。

### 1. “租户”就是你的新“实例”
OceanBase 采用**多租户架构**，一个集群可以划分出多个租户。你可以把租户理解为一个**逻辑上的数据库实例**——它既是数据库对象的容器，也是 CPU、内存、存储等资源的容器。

创建租户时，你可以选择兼容模式：**MySQL 模式**或 **Oracle 模式**。一旦选定就无法更改，所有数据类型、SQL 语法、系统视图都会向对应的数据库看齐。

### 2. 三种租户类型
在 OceanBase 中，你会接触到三种租户：
- **系统租户（sys租户）**：集群默认创建，负责管理集群和所有租户的生命周期。它本身是 MySQL 兼容模式的。
- **用户租户**：你真正打交道的“工作空间”，对外提供完整的数据库功能，支持 Oracle 或 MySQL 模式。
- **Meta租户**：系统为每个用户租户自动创建，用于存储该租户的私有元数据（如配置项、副本信息、日志流状态等），无需直接管理。

> ⚠️ 注意：OceanBase 社区版默认只提供 MySQL 模式的租户。如需 Oracle 模式，请确认使用的是企业版或云环境。

## 🧬 第二站：架构深潜——理解分布式数据库的“骨骼”

要精通，就必须理解其底层运转机制。

### 1. 原生分布式架构
OceanBase 是**原生分布式数据库**，基于 **Paxos 协议**保证多副本数据的强一致性，实现 **RTO < 30 秒**的高可用标准。其三大核心优势包括：
- **原生分布式架构**：分区技术支撑海量数据，多副本+自动选主实现高可用。
- **全栈 Oracle 兼容**：从数据类型、SQL 语法、存储过程到系统视图的全方位兼容。
- **极致性能**：TPC-C 基准测试 7.07 亿 tpmC 的成绩，性能表现领先。

### 2. 存储与资源隔离机制
在 OceanBase 中，**每个分区（Partition）都是一个独立的物理存储单元（Tablet）**。这意味着分区设计直接影响内存和存储效率。租户通过**资源池（Resource Pool）** 来限定所占资源量，资源池由**资源单元规格（Resource Unit）** 定义具体的 CPU 和内存配额。

## 🚢 第三站：部署实战——从零搭建你的第一个环境

### 1. 部署方案选择
- **开发测试环境**：推荐使用 All-in-One 安装包或 Docker 快速体验。
- **生产环境**：需采用 RPM 包部署多节点集群，**最少 3 个 Zone**，每个 Zone 建议部署 3 个 OBServer 节点，确保高可用性。

### 2. 关键操作路径
1.  **下载 OBD（OceanBase Deployer）**：官方自动化部署工具。
2.  **配置 YAML 文件**：需指定 Oracle 兼容模式。
3.  **部署集群**：执行部署命令。
4.  **验证状态**：使用 `obd cluster list` 和 `obd cluster display` 确认集群正常。

### 3. 创建你的 Oracle 租户
集群运行后，你需要创建一个 Oracle 模式的用户租户。关键步骤包括：创建资源单元规格 → 创建资源池 → 创建租户并指定 Oracle 兼容模式。租户创建成功后，即可通过客户端工具（如 DBeaver、Navicat、ODC）连接。连接时需注意：Oracle 模式租户的端口通常为 `1521`，用户名格式为 `用户名@租户名`。

## 🔄 第四站：迁移落地——从 Oracle 到 OceanBase 的实战心法

迁移绝非简单的“数据搬家”，而是一场思维与架构的重构。以下是来自真实项目踩坑后的宝贵经验。

### 1. 拒绝“无脑迁移”存储过程
**场景**：一个原本在 Oracle 中 30 分钟完成的批量任务，迁移到 OceanBase 后变成了 2 小时。
**根因**：存储过程中大量使用游标循环（`for rec in (select ..) loop insert; end loop;`），逐行处理在分布式架构下是性能杀手。
**解法**：
- **拥抱批处理**：将逐行插入改写为 `INSERT INTO ... SELECT ...` 集合操作。
- **使用 FORALL**：如在 PL 中保留计算逻辑，尽量使用批量 `FORALL` 语句减少上下文切换。

### 2. 警惕“小文件爆炸”——分区策略的降维打击
**场景**：沿用 Oracle 的复合分区策略（如按天 Range + 按地区 List），导致底层 Tablet 数量爆炸，耗尽内存。
**根因**：OceanBase 的每个分区都是物理存储单元（Tablet），过多的分区会耗尽内存资源。
**解法**：
- **简化分区设计**：非必要不采用复合分区，尽量使用一级分区。
- **利用自动分区能力**：使用 OceanBase 4.x 的自动分区分裂功能，让内核根据数据量自动管理分区大小。

### 3. Hint 的兼容陷阱
**场景**：Oracle 中的 `/*+ PARALLEL(8) */` 在 OceanBase 中不报错但不生效。
**根因**：OceanBase 拥有自己基于代价的分布式优化器，与 Oracle 并不完全一致。
**解法**：
- **清理无效 Hint**：系统性删除 Legacy Hint，避免干扰原生优化器。
- **关注 Leading Hint**：如确需干预，重点检查驱动表的指定是否正确——分布式环境下表连接顺序的影响远大于单机数据库。

### 4. 迁移工具选型
推荐使用官方迁移工具 **OMS（OceanBase Migration Service）** 完成结构迁移、全量迁移和增量同步。其他可选工具包括 DataX、OGG 等。迁移前务必使用**迁移评估工具**扫描对象依赖，生成兼容性报告。

## 🛠️ 第五站：运维精进——让 OceanBase 稳定奔跑

### 1. 日常管理要点
- **用户与权限**：沿袭 Oracle 风格，支持系统权限、对象权限和基于角色的访问控制（RBAC）。
- **事务与锁**：理解 OceanBase 如何保障 ACID，以及其锁机制与死锁监控方法。
- **备份与恢复**：掌握租户级别备份、全量恢复以及**闪回查询**等快速恢复手段。

### 2. 监控与诊断
- **OCP 平台**：OceanBase 云平台提供 300+ 个监控指标。
- **系统视图**：通过 `GV$` 系列视图扩展监控维度，分析会话状态和 SQL 性能。
- **执行计划分析**：使用 `EXPLAIN` 命令查看分布式执行计划，定位性能瓶颈。

### 3. 高可用容灾方案
- **同城三中心**：RPO=0，RTO < 30 秒。
- **两地三中心**：支持级联备库配置。
- **真实案例**：金华银行新一代核心系统采用“一主集群+三备集群”架构，实现 99.999% 业务连续性，批量代发时效提升 120 倍。

| **SQL 调优** | 依赖 Hint | 信任优化器，清理无效 Hint |
| **资源模型** | 实例独占 | 租户共享 + 资源隔离 |
