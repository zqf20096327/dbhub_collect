# naparnik-admin

Шлюз и админка для публичного API **«1С:Напарник разработчика»**. Подключает Напарника к любым современным IDE и агентам: приложение принимает запросы в форматах популярных провайдеров, транслирует их в API Напарника и возвращает ответ в формате выбранного клиента.

Один бинарник на Go, без Node.js и внешних зависимостей: SQLite встроена, интерфейс админки вшит через `go:embed`.

## Что умеет

**Входящие протоколы** (все — на одном порту):

| Протокол | Эндпоинт | Клиенты |
|---|---|---|
| OpenAI Chat Completions | `POST /v1/chat/completions`, `GET /v1/models` | Cline, Roo Code, Continue, Zed, JetBrains AI, ZCode |
| OpenAI Responses | `POST /v1/responses` | Codex CLI и другие клиенты нового формата |
| Anthropic Messages | `POST /v1/messages` | Claude Code, DeepSeek Harness |
| Gemini | `POST /v1beta/models/{model}:generateContent` и `:streamGenerateContent` | Gemini CLI |

Поддерживаются обычные и SSE-ответы, `tools` в обе стороны, `usage`, `naparnik_context` (заполненность контекста), авто-компактизация.

**Режимы потока**: `final` отдаёт весь ответ одним куском в конце, `deltas` — по мере готовности сообщений. Напарник присылает предварительные дельты (`content_delta`), которые вправе отфильтровать или переписать, поэтому шлюз их клиенту не отдаёт: в `deltas` каждое сообщение ассистента уходит одним куском сразу после финального пакета. Посимвольной «печати» нет, зато ответ всегда совпадает с подтверждённым сервером, а отфильтрованный текст не утекает в клиент. Промежуточные сообщения перед вызовом инструмента видны по мере готовности.

**Рассуждения**: `reasoning_content` Напарника транслируется в OpenAI-совместимые ответы — в не-стриме как `message.reasoning_content`, в потоке отдельными чанками `delta.reasoning_content`. Cline, Roo Code, Kilo Code и OpenCode показывают их как «размышления». Рассуждения берутся из подтверждённых пакетов, поэтому черновые мысли, которые сервер потом выбросил, до клиента не доходят.

**Ключи и токены**: один ключ Напарника → сколько угодно токенов (по одному на IDE или разработчика). Ключи шифруются AES-GCM, токены хранятся только хешем и показываются один раз при выпуске.

**Мониторинг**: расход и остаток по каждому ключу (5-часовое и недельное окна), графики, разбивка по токенам, оценка «сколько запросов осталось», webhook-алерты по порогам.

**Журнал запросов**: видно, что именно спрашивали — последняя реплика пользователя (до 2000 символов) вместе с токеном, протоколом, статусом и задержкой. Клик по строке (или иконка «глаз») открывает карточку записи: полный текст вопроса с копированием, ключ и токен, протокол и модель, токены запроса, ответа и из кэша, задержка, текст ошибки. Записи листаются по 50, есть кнопка обновления списка. Журнал выгружается в CSV (UTF-8 с BOM, разделитель «;» — открывается в Excel), а старые записи удаляются прямо из админки: указываешь число дней, `0` — очистить всё. Текст вопросов лежит в базе в открытом виде, поэтому журнал стоит чистить по регламенту.

**Слушатели**: несколько портов одновременно, `0.0.0.0` для доступа из локальной сети, правка списка из админки без перезапуска. Каждый слушатель можно выключить переключателем — порт закроется, а запись останется в конфиге (`disabled: true`), чтобы потом включить обратно. Последнюю админку выключить нельзя. Любой слушатель можно перевести на HTTPS: укажите пути к сертификату и ключу (PEM) — кнопка с замком в строке слушателя. Кнопка «Применить» перезаписывает `listeners` в `config.yaml` целиком, поэтому комментарии в этом файле не сохраняются — держите ручные пометки вне конфига.

**Интерфейс админки**: тёмная и светлая тема — переключатель-иконка в правом верхнем углу, выбор запоминается в браузере и применяется до первой отрисовки. Вёрстка адаптивная: на узких экранах сайдбар убирается в выдвижное меню с бургером. Всё на чистом HTML/CSS/JS без сборки фронтенда.

**Подключение**: мастер подключения. Сверху плитки клиентов с отметкой «Проверено» / «Не проверено» — Cline, Roo Code / Kilo Code, Continue, Zed, JetBrains AI Assistant, Qoder, Claude Code, Codex CLI, Gemini CLI, OpenCode и проверка через curl. Выбираете плитку, токен и адрес шлюза — внизу собирается готовая инструкция с реальным значением токена и копируется одной кнопкой. Если у токена ограничен протокол, мастер предупредит о несовпадении с выбранным клиентом.

**Настройки**: ID модели для подключения, режим потока, порог авто-компактизации, TTL сессии, таймаут запроса, период опроса бюджета, пороги алертов и webhook. Длительности вводятся числом с единицей (`30s`, `5m`, `2h`) — формат подсказан в интерфейсе и проверяется и на клиенте, и на сервере.

## Быстрый старт

```bash
go build -o bin/naparnik-admin ./cmd/naparnik-admin
cp config.example.yaml config.yaml
./bin/naparnik-admin -config config.yaml serve
```

Откройте <http://127.0.0.1:47830>, задайте пароль администратора, добавьте ключ Напарника (из <https://code.1c.ai>), выпустите токен — и подключайте IDE.

### HTTPS

Слушатель переводится на HTTPS парой файлов: сертификат (PEM, можно с цепочкой) и ключ (PEM, без пароля). Пути задаются в `config.yaml` или кнопкой с замком на странице «Слушатели». Работает TLS 1.2 и новее.

```yaml
listeners:
  - addr: 0.0.0.0:47833
    kind: gateway
    cert_file: /etc/naparnik/server.crt
    key_file: /etc/naparnik/server.key
```

Правила:

- **Нужны оба файла.** Если заполнен только один, сервер откажет с понятной ошибкой: молчаливого отката к HTTP не будет.
- **Пара проверяется до применения.** Битая пара или отсутствующий файл — ошибка сразу, работающие порты при этом не трогаются.
- **Смена сертификата не требует перезапуска.** Слушатель пересоздаётся при «Применить» и подхватывает новый файл.
- **Сниппеты подключения становятся `https://`.** Мастер в админке подставляет схему по факту TLS у выбранного шлюза.
- **Cookie админки получает `Secure`** на HTTPS-запросах, поэтому по HTTP она не утечёт.
- **Сертификат должен быть доверенным для клиентов.** Самоподписанный подойдёт для стенда, но Cline, Zed и остальные потребуют добавить его в доверенные или отключить проверку — надёжнее выпустить сертификат у корпоративного CA. Шлюз сертификаты не выпускает, только использует готовые.

### Подключение IDE

**Проверено реальным подключением:** Cline, Zed, Qoder, OpenCode, ZCode, проверка через curl.

Живые проверки шли через `http://aids:47833/v1` (сетевой адрес стенда): `/v1/models`, стрим, многоходовый диалог, вызов клиентского инструмента и продолжение после его результата, rewind истории.

**Ещё не проверено** (инструкции рабочие, но подключение в этих клиентах не подтверждалось): Roo Code / Kilo Code, Continue (VS Code, JetBrains), JetBrains AI Assistant, Claude Code, Codex CLI, Gemini CLI.

Точные настройки для каждого клиента собирает мастер в разделе «Подключение» админки — там же актуальные адрес шлюза и значение токена. Ниже — те же варианты текстом.

**Cline / Roo Code / Continue / Zed** — провайдер «OpenAI Compatible»:

```
Base URL: http://127.0.0.1:47831/v1
API Key:  nr_...            (токен из админки)
Model:    naparnik          (id модели из настроек админки)
```

**Claude Code**:

```bash
export ANTHROPIC_BASE_URL=http://127.0.0.1:47831
export ANTHROPIC_API_KEY=nr_...
claude
```

**Gemini CLI**:

```bash
export GOOGLE_GEMINI_BASE_URL=http://127.0.0.1:47831
export GEMINI_API_KEY=nr_...
gemini
```

### Служба Windows

Установка не требует NSSM и сторонних утилит — служба регистрируется напрямую в SCM. Команды выполняйте в консоли **от имени администратора**:

```bat
bin\naparnik-admin.exe -config C:\naparnik-admin\config.yaml service install
bin\naparnik-admin.exe service start
bin\naparnik-admin.exe service status
bin\naparnik-admin.exe service stop
bin\naparnik-admin.exe service remove
```

Что важно знать:

- служба ставится с автозапуском и именем `naparnik-admin`;
- путь к конфигурации сохраняется абсолютным, а рабочая папка при старте переносится к конфигу — поэтому относительный `data_dir` разрешается рядом с `config.yaml`, а не в `C:\Windows\System32`;
- под SCM stdout не сохраняется, журнал пишется в `<data_dir>\service.log`;
- `service status` и остальные команды требуют прав администратора, иначе SCM вернёт `Access is denied`;
- после правки `config.yaml` службу нужно перезапустить (`stop` + `start`).

### CLI без админки

```bash
./bin/naparnik-admin -config config.yaml key add -name "Отдел" -key <ключ Напарника>
./bin/naparnik-admin -config config.yaml token create -key-id 1 -name "Cline" -ide Cline

```

## Конфигурация

```yaml
data_dir: ./data
model_id: naparnik          # id модели для IDE, меняется в настройках админки
listeners:
  - addr: 127.0.0.1:47831   # шлюз
    kind: gateway
  - addr: 0.0.0.0:47832     # шлюз для локальной сети
    kind: gateway
  - addr: 127.0.0.1:47830   # админка
    kind: admin
stream_mode: final          # final | deltas
auto_compact_at: 0.85
budget_poll_interval: 5m
session_ttl: 2h
request_timeout: 10m
warn_percent: 80
crit_percent: 95
alert_webhook: ""
```

Переменные окружения: `NAPARNIK_ADMIN_DATA_DIR`, `NAPARNIK_ADMIN_MASTER_KEY` (base64, 32 байта), `NAPARNIK_ADMIN_UPSTREAM`, `NAPARNIK_ADMIN_MODEL_ID`.

`model_id` — публичное имя модели: его показывают сниппеты подключения и `GET /v1/models`, а запросы с этим именем принимаются как обычно. В API Напарника имя не передаётся, так что менять его можно свободно (латиница, цифры, `- _ . : /`). Правится в разделе «Настройки» без перезапуска.

Мастер-ключ при первом запуске генерируется в `data/master.key` (права 0600). Без него нельзя расшифровать ключи Напарника — сохраните его вместе с базой.

## Как это работает

```
IDE ──(OpenAI / Anthropic / Gemini)──▶ шлюз ──▶ code.1c.ai/public/v1
                                         │
                                  SQLite: ключи, токены,
                                  сессии, замеры бюджета,
                                  журнал запросов
```

- **Сессии.** Заголовки `x-session-id` / `x-deepseek-harness-session-id` привязывают клиентскую сессию к диалогу Напарника. Если заголовка нет (Cline, Continue, Roo Code), сессия строится по отпечатку первого сообщения чата: у каждого чата одного токена свой диалог и своя очередь. Разные чаты работают параллельно и не пересоздают диалог друг друга, а запросы внутри одного чата идут по очереди — диалог у Напарника линейный. Диалог переиспользуется, пока не истёк TTL.
- **Очередь сессии.** Запросы одной сессии выполняются строго по очереди — диалог у Напарника линейный. Если запрос встал в очередь, поток открывается сразу и держится пингами каждые 15 с: клиент не видит молчащее соединение и не обрывает его по своему таймауту. Запросы разных сессий и разных чатов одного токена идут параллельно.
- **Экономия лимита.** В существующий диалог отправляется только хвост истории после последней реплики ассистента — остальное уже хранится на сервере Напарника.
- **Инструменты.** Имена клиентских функций получают префикс (`client_…`), чтобы не конфликтовать с серверными. Вызовы серверных инструментов (поиск по ИТС) подтверждаются автоматически, поток держится пингами.
- **Поток.** Черновики Напарника (`content_delta`) клиенту не транслируются: сервер может их отфильтровать или переписать, поэтому источник истины — финальный пакет. `final` отдаёт всё в конце, `deltas` — каждое подтверждённое сообщение сразу, по мере готовности. Ошибки до первого байта уходят обычным JSON с корректным HTTP-кодом, а не обрывком потока.
- **Контекст.** `context_tokens` запрашивается после ответа; при заполнении выше `auto_compact_at` вызывается `compact`.

## Мониторинг: что можно и чего нельзя показать

API Напарника отдаёт **только проценты** (`used_percent`) и время сброса по двум окнам — 5 часов и неделя. Абсолютные квоты в запросах или рублях не публикуются.

Поэтому в админке:

- **факт** — процент расхода, остаток (`100 − used`), время до сброса, статус ключа;
- **оценка** (помечена как оценка) — процент на запрос по приращению между замерами, сколько запросов осталось, прогноз исчерпания окна;
- **своя статистика** — запросы, токены, задержки, ошибки, разбивка по токенам.

Опрос `/budget` лимит не расходует, поэтому бюджеты снимаются каждые 5 минут и по кнопке «Обновить».

## Ограничения

- Только текст: изображения и вложения отклоняются с понятной ошибкой (API Напарника их не принимает).
- `temperature`, `top_p`, `max_tokens`, `response_format` не передаются — движок Напарника их через публичный API не применяет. Поля принимаются и игнорируются, чтобы клиенты не падали.
- Один процесс = одна база. Не запускайте два экземпляра на одном `data_dir`.

## Windows и кириллица

Если отправлять запросы через `curl` в консоли Windows, русский текст уходит в cp1251 и тело перестаёт быть валидным UTF-8. Шлюз такие запросы отклоняет с кодом 400 и подсказкой. Используйте `--data-binary @file.json` с файлом в UTF-8 — или IDE, которая всегда шлёт UTF-8.

## Разработка

```bash
make build   # собрать бинарник
make test    # go test ./...
make vet     # go vet ./...
make run     # запустить с config.yaml
make icon    # иконка и версия в EXE (нужен go-winres)
```

Структура: `cmd/` — CLI, `internal/naparnik` — клиент API Напарника, `internal/gateway` — сессии и маршрутизация инструментов, `internal/protocol/*` — адаптеры протоколов, `internal/monitor` — бюджеты и статистика, `internal/admin` + `internal/web` — админка (SPA и статика в `internal/web/assets`), `branding/` — исходники фирменного стиля: логотипы, иконки, баннер для GitHub.
