## Зачем нужны Agent Skills

AI-ассистенту недостаточно знать синтаксис Go. Ему нужно учитывать архитектуру конкретного проекта, распространение context, завершение goroutines, обработку ошибок, тестируемость и ограничения production. Навык содержит короткие инструкции, критерии проверки и примеры вместо универсального промпта на сотни строк.

## Быстрый старт

1. Изучите нужный раздел и подключите соответствующий SKILL.md через механизм навыков вашего клиента.
2. Укажите агенту задачу и ограничения проекта: версия Go, зависимости, контракт API и критерии готовности.
3. Проверьте результат самостоятельно: компиляция, тесты, анализ гонок и ревью diff.

## 1. Архитектура Go-сервиса

Начинайте с простой структуры. Выделяйте пакеты по ответственности, а не по абстрактным слоям без логики.

```text
cmd/api/main.go       # конфигурация и сборка приложения
internal/order/       # бизнес-правила
internal/httpapi/     # HTTP-транспорт
internal/postgres/    # реализация хранения
```

Интерфейс объявляется рядом с потребителем. Доменная логика не должна зависеть от HTTP-фреймворка или конкретной базы. Перед созданием интерфейса ответьте: есть ли реальная граница или потребность подменить зависимость?

## 2. Ошибки в Go

```go
if err != nil {
    return fmt.Errorf("load order %d: %w", id, err)
}
```

Используйте errors.Is для сравнения известных ошибок и errors.As для извлечения типа. Добавляйте смысловой контекст на границе уровня; не логируйте одну ошибку в каждом слое. Не заменяйте ошибку на nil и не используйте panic для обычных отказов ввода.

## 3. Goroutines, channels и context

Каждая goroutine должна иметь определенного владельца и условие завершения. Передавайте context первым параметром. Вызывайте cancel после context.WithTimeout. Не запускайте новую goroutine для каждого элемента бесконечного потока: ограничивайте параллелизм.

```go
select {
case <-ctx.Done():
    return ctx.Err()
case jobs <- job:
    return nil
}
```

Отправитель закрывает канал, если владеет его жизненным циклом. Для защиты общей map используйте mutex или архитектуру с одним владельцем. Проверяйте гонки командой go test -race ./....

## 4. HTTP API и микросервисы

Для небольшого сервиса достаточно net/http. Добавляйте сторонний роутер, когда действительно нужны его возможности. Настройте ReadHeaderTimeout, IdleTimeout и политику обработки больших запросов; передавайте context в запросы к зависимостям. Завершайте сервер через Shutdown с ограниченным временем.

| Ответ | Когда возвращать |
|---|---|
| 400 | Некорректный формат или входные данные |
| 404 | Ресурс не найден |
| 409 | Конфликт состояния |
| 429 | Превышен лимит |
| 500 | Неожиданная внутренняя ошибка |

## 5. PostgreSQL и database/sql

sql.DB - пул соединений. Создавайте его один раз на приложение, настраивайте лимиты с учетом количества реплик и бюджета базы. Используйте QueryContext/ExecContext и параметры запросов; проверяйте rows.Err после обхода. Транзакции должны быть короткими, rollback должен выполняться при преждевременном выходе, а ошибка Commit - проверяться.

Не запускайте внешние сетевые операции внутри длительной транзакции. Для надежной доставки событий после записи изучите transactional outbox.

## 6. Тестирование Golang

```bash
go test ./...
go test -race ./...
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

Table-driven tests подходят для граничных значений. httptest - для HTTP-контрактов. Интеграционные тесты нужны там, где поведение зависит от реальной БД. Не проверяйте внутреннюю реализацию вместо наблюдаемого результата.

## 7. Производительность и профилирование

```bash
go test -bench=. -benchmem ./...
go test -run='^$' -bench=. -cpuprofile=cpu.out ./internal/example
go tool pprof cpu.out
```

Для профиля укажите конкретный пакет. Сравнивайте несколько прогонов в одинаковых условиях. Сначала найдите горячий участок, затем меняйте алгоритм или аллокации. Не внедряйте sync.Pool без измерений.

## 8. Observability и надежность

Используйте структурированные логи slog, корреляцию запроса через request ID, метрики latency, traffic, errors и saturation. Не записывайте персональные данные и токены в логи. Ограничивайте число уникальных значений labels. Повторяйте только временные ошибки и только безопасные для повторения операции; учитывайте общий deadline и backoff.

## 9. Чек-лист перед pull request

- [ ] gofmt, go vet и тесты проходят.
- [ ] Нет изменений публичного API без описания миграции.
- [ ] Ошибки не теряются, ресурсы освобождаются.
- [ ] Есть остановка фоновых задач.
- [ ] Изменения схемы БД совместимы с развертыванием.
- [ ] Нет секретов, лишних зависимостей и незапланированных сетевых запросов.
- [ ] Производительность подтверждена измерениями, если она была целью.

## 10. Готовые задания для AI-агента

| Задача | Промпт |
|---|---|
| Рефакторинг | Изучи код, предложи минимальные изменения, сохрани контракт, добавь тесты |
| Code review | Найди ошибки обработки context и жизненного цикла goroutines в моем diff; объясни и предложи исправления |
| API | Реализуй обработчик net/http, валидацию, тесты httptest и graceful shutdown |
| Оптимизация | Запиши benchmark до изменений, выяви аллокации, сравни измерения |
| Работа с БД | Проверь транзакционные границы, ошибки Commit, лимиты пула и context |
