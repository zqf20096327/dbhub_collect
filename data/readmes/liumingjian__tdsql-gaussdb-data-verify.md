# TDSQL to GaussDB Data Verification

Design notes for a lightweight offline data verification tool for migrations from centralized TDSQL MySQL to centralized GaussDB 25.1.32 O-mode.

The first version focuses on post-migration data consistency and completeness checks for business tables. It verifies only the database metadata required to make that check safe, including Comparison Key column metadata and ordering-index support; it does not verify unrelated database objects such as triggers, stored procedures, permissions, or sequences.

## Current Scope

- Offline full verification after a confirmed migration completion point or data freeze window.
- P0 production verification uses streaming two-way merge ordered by Comparison Key, with bounded row-level Difference Detail; ADR-0032 supersedes Merkle / digest-tree and keyset Chunk comparison for P0 while retaining them as future work.
- Explicit table scope through selected tables or whole-database candidate discovery with include and exclude wildcard rules.
- Source-to-target table mapping, with same-name automatic matching and manual mapping for renamed tables.
- Value normalization before comparison to reduce false differences between TDSQL MySQL and GaussDB O-mode.
- Precheck before verification, with batch-level blockers and table-level warnings, degraded checks, or skipped tables.
- Table-oriented reports in Excel, CSV, and clean static HTML.

## Quick start from the deploy package

Build and materialize the portable deployment directory:

```sh
./gradlew clean test assembleDeploy
```

The generated `deploy/` directory contains executable commands in `bin/`, all Java and JDBC dependencies in `lib/`, a safe TOML template in `conf/conf.toml`, and the complete quick-start guide in `docs/QUICK_START.md`.

```sh
cp deploy/conf/conf.toml /path/to/my-conf.toml
export DB_VERIFY_SOURCE_PASSWORD='<set locally>'
export DB_VERIFY_TARGET_PASSWORD='<set locally>'
deploy/bin/tdsql-gaussdb-verify --config /path/to/my-conf.toml
```

`db-verify` is a one-shot CLI: each invocation runs `Precheck -> Verify -> Report` and then exits, so there is no separate daemon stop command. `deploy/bin/db-verify.sh` is provided as a compatibility alias. Passwords must remain in the named process environment variables and must not be written to TOML or command-line arguments.

See [docs/QUICK_START.md](docs/QUICK_START.md) for configuration, exit-code, output, and troubleshooting details.

## MVP Usage

Run the customer-facing Java launcher with a TOML configuration:

```sh
./gradlew installDist
bin/tdsql-gaussdb-verify --config examples/jdbc-fixed-scenario.toml
```

The MVP executes `Precheck -> Verify -> Report`, connects through JDBC to the Source Database and Target Database, applies explicit Table Mapping, compares rows by Comparison Key after common value normalization, records bounded Difference Detail, and writes reports under the configured output directory.

Exit codes:

- `0`: verification completed and all eligible Business Tables passed.
- `1`: verification completed and data differences were found.
- `2`: Precheck found batch-level blockers.
- `3`: runtime failure.
- `4`: user or argument cancellation.

Reports generated by the MVP:

- `batch-summary.csv`
- `table-summary.csv`
- `scope-summary.csv`
- `selection-rules.csv`
- `execution-parameters.csv`
- `warning-tables.csv`
- `skipped-tables.csv`
- `difference-detail.csv`
- `report-paths.csv`
- `verification-report.html`
- `verification-report.xlsx`

The launcher is dependency-free shell and requires Java. Build with `./gradlew installDist`; no Node runtime is used.

Execution parameters default conservatively and can be tuned globally or per table:

```yaml
execution:
  tableConcurrency: 1
  chunkSize: 1000
  detailLimit: 100
  queryTimeoutMs: 30000
  retryCount: 1
  throttleMs: 0
  tables:
    - table: customer_account
      chunkSize: 500
      queryTimeoutMs: 60000
      retryCount: 2
```

Invalid execution values are Precheck blockers. Table-level query timeouts or retry exhaustion are recorded as failed table results; unrelated eligible tables continue and the batch returns the runtime failure exit code after writing reports.

## Fixed First-Version Test Environment

Issue 3 establishes one fixed scenario environment for first-version development and regression work. No other first-version test environments are preset.

Start the source-side MySQL 8 container:

```sh
export TDSQL_SOURCE_ROOT_PASSWORD='<set locally>'
export TDSQL_SOURCE_PASSWORD='<set locally>'
docker compose -f test-environment/mysql8/docker-compose.yml up -d
```

The MySQL container initializes `tdsql_verify_fixed` from:

- `test-environment/sql/mysql/00-reset.sql`
- `test-environment/sql/mysql/01-baseline.sql`

To reset the source scenario data after the container is running:

```sh
docker compose -f test-environment/mysql8/docker-compose.yml exec -T tdsql-mysql8 mysql -uroot -p"$TDSQL_SOURCE_ROOT_PASSWORD" < test-environment/sql/mysql/00-reset.sql
docker compose -f test-environment/mysql8/docker-compose.yml exec -T tdsql-mysql8 mysql -uroot -p"$TDSQL_SOURCE_ROOT_PASSWORD" tdsql_verify_fixed < test-environment/sql/mysql/01-baseline.sql
```

Prepare the target-side GaussDB connection from `test-environment/gaussdb/target-connection.template.yml`. The fixed target is host `10.250.0.157`, port `8000`, database `testdb`, user `tom`; set the password outside the repository:

```sh
export GAUSSDB_TARGET_PASSWORD='<set locally>'
```

Apply the target reset and baseline SQL to the configured GaussDB schema:

```sh
gsql -h 10.250.0.157 -p 8000 -d testdb -U tom -f test-environment/sql/gaussdb/00-reset.sql
gsql -h 10.250.0.157 -p 8000 -d testdb -U tom -f test-environment/sql/gaussdb/01-baseline.sql
```

The deterministic expected results for later CLI assertions are recorded in `test-environment/scenario-matrix.json`. The baseline covers same-name table pass, Table Mapping pass, row count differences, missing Comparison Key, Column Consistency warnings, normalizable type differences, incompatible types, Difference Detail threshold cases, `NULL` versus empty string, large text, binary values, include/exclude rules, Precheck blockers, and invalid Execution Parameters.

## First Runnable CLI Slice

Build the tool and run the customer-facing launcher:

```sh
gradle build
bin/db-verify.sh --help
bin/db-verify.sh --config conf.toml
```

The Java CLI executes the Single Entry CLI workflow `Precheck -> Verify -> Report` against JDBC connections. TOML is parsed inside the Java application, Verification Batch IDs are generated by the system, passwords are loaded from explicitly named environment variables, and generated logs/reports mask Connection Secrets.

The CLI writes artifacts under `report.output_dir/<generated-batch-id>/`; when `report.output_dir` is absent, the output root is `./db-verify-reports` relative to the current working directory. Relative configured output directories also resolve against the current working directory, and existing run directories are never overwritten.

- `db-verify.log`
- `report.html`
- `table-summary.csv`

Exit codes:

- `0`: clean pass
- `10`: data differences found
- `20`: blocked by Precheck
- `64`: argument or user error
- `70`: runtime failure

Minimal configuration example:

```toml
[source]
url = "jdbc:mysql://source.example:3306/app?useCursorFetch=true&useServerPrepStmts=true"
username = "source_user"
password_env = "DB_VERIFY_SOURCE_PASSWORD"
schema = "app"

[target]
url = "jdbc:gaussdb://target.example:8000/app"
username = "target_user"
password_env = "DB_VERIFY_TARGET_PASSWORD"
schema = "app"

[tables]
include = ["customer_*"]
exclude = ["customer_tmp"]
default_key = ["id"]

[tables.mapping]
legacy_customer = "customer"

[tables.keys]
customer_account = ["tenant_id", "id"]

[execution]
table_concurrency = 2

[report]
output_dir = "build/db-verify-reports"
```

Set `DB_VERIFY_SOURCE_PASSWORD` and `DB_VERIFY_TARGET_PASSWORD` in the process environment rather than committing credentials in TOML. The optional `execution.table_concurrency` accepts only `1` or `2`; omitting it preserves sequential configuration-order execution with the conservative default of `1`. At `2`, eligible Business Tables use at most two workers, each with independent Source Database and Target Database connections, while results and reports remain in configuration order.

TOML stores only non-sensitive connection settings: JDBC URL, username, optional schema, report output, table include/exclude rules, same-source-to-target table mapping for renamed tables, and Comparison Key configuration. Source and target passwords must use separate environment variables through `source.password_env` and `target.password_env`; inline passwords and password command-line overrides are rejected. Internal execution defaults such as fetch size and driver behavior are not user-facing TOML keys.

### Production Comparison Key Index Policy

Production verification is read-only and should be run only after selecting approved representative Business Tables in a Stable Data State. Precheck reads JDBC metadata for the configured Comparison Key and does not execute `COUNT DISTINCT`, `GROUP BY`, or extra full-table uniqueness scans.

Text, time, floating-point, binary, boolean, UUID-like text, and vendor-specific keys remain outside P0. P0 Comparison Keys are limited to compatible exact numeric columns; unsupported key types must block the table with a typed cause instead of falling back to string ordering.

For each table, Source Database and Target Database must each have verified JDBC metadata evidence for an index whose leading columns match the configured Comparison Key field order. Missing support or unavailable/unperformed metadata is a table-level Precheck blocker under the current conservative policy because the generated `ORDER BY` may otherwise require an expensive database-side sort.

This fail-closed blocker is an interim policy pending read-only calibration with the delivered TDSQL/MySQL and GaussDB drivers on approved representative tables. Generic H2 metadata tests do not establish vendor query-plan behavior, so the final warning-versus-blocker thresholds remain incomplete until that production evidence is recorded.

Unique constraints or unique indexes are reported separately as metadata evidence only. They are not a substitute for the main scan, which still validates actual NULL keys, duplicate keys, and strict ordering while reading rows.

### P0 Final Acceptance Gate

P0 cannot be declared production-ready until the full evidence bundle passes. The required bundle includes a clean full-suite run, H2 generic JDBC integration tests, real-driver read-only TDSQL/MySQL and GaussDB production runs, two fixed-small-heap row-count scales, high-difference-rate evidence, report consistency checks, `git diff --check`, and a review against the starting worktree diff confirming existing report and DifferenceSample work was not overwritten.

If live database credentials, Stable Data State, approved representative tables, fixed-heap execution, or high-difference-rate production evidence are unavailable, record the missing external gates and do not claim P0 has reached production readiness.

## Canonical real E2E workflow

The canonical real E2E workflow is documented in [docs/acceptance/real-e2e-workflow.md](docs/acceptance/real-e2e-workflow.md). It uses `examples/production-e2e.toml` and the guarded `scripts/e2e/db-verify-e2e.sh` interface:

```sh
scripts/e2e/db-verify-e2e.sh preflight
scripts/e2e/db-verify-e2e.sh full-readonly
```

Readonly evidence requires explicit non-secret gates (`DB_VERIFY_READONLY_APPROVED=YES` and `DB_VERIFY_STABLE_DATA_STATE=YES`) before the product launcher runs. Evidence is written under `/tmp/db-verify-e2e/evidence/<run-id>`, reports under `/tmp/db-verify-e2e/reports`, and exit code `10` means data differences were found rather than runner failure.
