# MathAgent

面向数学教师的私有部署智能批阅工作台：导入试卷或答题卡，完成模板确认、学生 OCR、数学判分、教师复核、统计和报告导出。

官网：<https://www.mathagent.com.cn>

> **一句话结论**：同一张卷、同一句「转录这份试卷。」，原图 **46/50** 次把学生的错答 `4√5` 直接写成正确答案 `4/5`，50 次没有一次如实；把印刷题干差分掉之后 **0/50** 改写、50 次全部如实。试过的 3 种提示词都没压到 0，差分掉题干是这组实验里唯一做到 0 的改动（单卷单题，每组 50 次）—— [证据与 200 条原始回执](evidence/03_prompt-context-leak/)。

## 两大亮点

| | 亮点 | 解决的问题 | 关键数字 |
|---|---|---|---|
| ① | **差分掉印刷题干**（[原理与效果图](#a-差分管线与三道闸)） | 模型无题干可借，不会把学生的错答「改成」正确答案 | 改写 **46/50 → 0/50**；转录准确率 **97.2% → 99.6%**；平均输出 2556 → 468 字符、耗时 21.5 s → 5.0 s |
| ② | **按题分片 + 跨页尾块**（[示意图](#b-按题分片与跨页尾块)） | 跨页续题的题干上下文完整，模型不自编条件 | 尾块从上一页最后一题的题号上沿裁到页底，余量 **1.5%**；只追加给负责该题的那一路请求，**不新增调用** |

下文按「发现问题 → 痛点 → 如何思考 → 解决方案 → 最终效果」展开；私有部署、模型密钥加密存储等配套见[部署与运维](#部署与运维)。

## 从发现问题到解决

### 1. 如何发现的问题

起点是一次教学见习。我想用 AI agent 替老师完成两件事：课后作业批改和错题数据整理。第一次试跑就撞上了问题——30 张试卷批了近 50 分钟，而且结果里出现大量「误判」，方向很反常：分数普遍偏高。作为带过这些学生的老师，我清楚有些人不可能打出那个分数。这个直觉提醒我：问题可能不在学生，而在批阅本身。

我做了一个验证：要求模型把它看到的答案原样转录出来，再与原卷对照——模型不是看错了，而是把学生的错答「改」对了：卷面上是错误答案，转录出来却是正确的。对这类产品，这是最致命的失败形态：分数好看了，教师看不出问题，学生拿不到真实反馈，错题整理更是建立在失真数据上。

### 2. 痛点在哪

这类产品最致命的失败不是判错，而是**把错的判成对的**：分数好看了，教师看不出问题，学生也拿不到真实反馈。判错的题在教师复核时还有机会被发现；被「改对」的错答混在好看的分数里，没有人会回头查。整个架构的取舍都围绕这一点。

它也不是换一句提示词就能压住的偶发现象。用同一张卷、同一道题（学生写 `4√5`，标准答案 `4/5`）、同一模型，只换输入和提示词，各跑 50 次（[`evidence/03_prompt-context-leak`](evidence/03_prompt-context-leak/)）：

| 输入 | 提示词 | 写成正确答案 `4/5` | 写成 `4√5/5` | 抄 `4√5` 但加注「应为4/5」 | 如实只抄 `4√5` |
|---|---|---|---|---|---|
| 原图（含印刷题干） | 「转录这份试卷。」 | **46 / 50** | 2 | 0 | **0**（另 2 次没给答案） |
| 原图（含印刷题干） | 「转录这份试卷，不要看题干，不要计算，直接转录。」 | **23 / 50** | 2 | 12 | 2（另 11 次没给答案或只抄题干） |
| 原图（含印刷题干） | 只要求输出作答 JSON（无防猜规则） | 0 | 8 | 0 | 42 / 50 |
| **差分图（题干已被减掉）** | 同一句「转录这份试卷。」 | **0 / 50** | 0 | 0 | **50 / 50** |

另一轮实验（[`evidence/01_difference-vs-raw`](evidence/01_difference-vs-raw/)）用生产提示词（含「题干、标准答案和数学知识不能作为转录依据」）：原图 6/10 读成 `4√5/5`、4/10 保留学生原答案，差分 0/10。

其中一次裸提示词的输出直接把学生的 `4√5` 换成 `4/5`，另一次先抄了 `4√5` 又自己补一句「此处手写答案有误，应为 4/5」。

**这不是提示词不够严**：生产提示词已经写明「题干、标准答案和数学知识不能作为转录依据」，仍然有 6/10 读成 `4√5/5`；反过来，不含任何防猜规则、只要求输出 JSON 的提示词是 8/50——每格 50 次仍然分不清提示词之间谁更好（95% 区间互相重叠），能确定的只是原图配哪种都不是 0。提示词只改变发生概率，**这组数据里唯一做到 0 的是让模型看不到题干**——差分把印刷题干减掉，模型没有可借用的上下文，只能认字，判断因此完全落在识别能力上。

### 3. 如何思考的

先回答「模型为什么会改答案」。我注意到一个关键的不对称：它几乎只往「对」的方向改，不往「错」的方向改。如果是识别噪声，分数的增减应当大体随机；单向偏置只有一种解释——模型看到了印刷题干，自己算出了正确答案，然后「顺手改对」。

为了验证，我做了消融实验：把误判率最高的几道题的作答区单独裁剪后发给模型（不带题干）。结果大多数原先「识别错」的答案都识别对了——识别能力本身够用，病因是题干污染；少数仍读不出的，属于个别模型手写识别能力不足，与题干无关。方向从此确定：与其在提示词里求模型「别看题干」，不如让题干在输入阶段就不存在。

这个结论是花成本换来的。三种提示词按顺序试过：裸的「转录这份试卷」、加「不要看题干不要计算直接转录」、只要求结构化 JSON 输出——没有一种能把改答案压到 0。探索期先后试过 15 个以上的多模态模型、累计上千次调用，结论一致：换模型、换提示词都只改变发生概率，不消除它。最终保留下来的对照实验（三种提示词各 50 次 + 差分 50 次，200 条原始回执）在 evidence/03。

微调路线实测过，放弃。云端官方微调服务速度和质量都不达标；本地 8GB 显卡只够对 7B 级开源多模态模型做外挂秩（LoRA），推理慢且无法并发，对学校私有部署场景来说经济上也不成立。所以走工程路线：印刷题干是固定内容，同一套模板可以用 OpenCV 对齐后整幅减掉——差分之后只剩学生笔迹，模型无题干可借、只能认字，判断完全回到识别能力上。这条路还顺带带来速度和 token 收益：模型不用读题干，也不用把题干再抄一遍。

第二个亮点来自学习迁移。学到视觉模型处理长内容的「分片重叠」手法（避免上下文丢失）时，我立刻联想到自己多页模板链路上的一个已知问题：跨页续题的题干在上一页，本页的解题/转录请求根本看不到它，模型会自编条件。

解法是两个「废产物和副产物」的组合，这是这个项目里我最得意的决策之一：

- 切点用题号上沿——来自一条已废弃的第三方云教育 OCR 路线的经验：早期误以为误判是「模型注意力不集中」，用它做题目分块，它做不到一题一块，但相邻作答区的上沿相互分割，能形成几题一块的良好分块；
- 题号锚定——原本为了提速让定位与解题两路大模型并发，并发可能导致题号错位、后端无法合并，于是先发一路轻量模型确定一二级题号；结果发现它的题号定位也很准，就保留了下来。

分片本来就要按题裁图，「上沿切点 + 题号锚定」拼在一起就是上一页尾块：从上一页最后一题题号的上沿裁到页底，只追加给负责该续题的那一路解题/转录请求、作为最后一张图——不污染其它题，也不增加额外调用。参数和验收由我把关：余量最初 3%，我在测试图上看到它把上一题最后一行整行带了进来，压到 1.5%；验收方式是让参数（切线、余量）直接画在试卷图上，我逐张目检。

诚实地说：跨页上下文截断目前是「已知问题 + 针对性缓解」，没有完全解决，余量可能还要再压小——这个边界写在这里，不回避。

整个项目的分工是：我发现问题、定方向、定参数和验收标准；代码大部分由 AI 辅助实现，我逐行审查。

### 4. 解决方案

#### A. 差分管线与三道闸

![差分原理：教师冻结模板与学生卷对齐相减，抹掉残留虚线，只留笔迹；转录只看差分图，判分只收文本](docs/readme-assets/difference-pipeline.svg)

生产链路用模板差分而不是原图，目的不是让图更清楚，而是让印刷题干在输入阶段就不存在——模型没有可借用的上下文，只能认字，判断完全回到识别能力上。印刷题干是固定内容，同一套模板教师确认一次即可反复使用：

1. **对齐**：学生卷与教师冻结的模板做 OpenCV 特征匹配（SIFT + RANSAC 单应矩阵），透视对齐到模板坐标；
2. **差分**：对齐后与模板相减，印刷题干、选项、页眉被整幅减掉，只留学生笔迹和蓝色 Q 题号标签（`services/template_evidence.py`，复算入口 `TemplateEvidenceMatcher.match_and_build()`）；
3. **抹残留虚线**：证据里记录了反例——残留的印刷虚线会把连写的 `ab` 拆成 `a,b`，所以差分后还要抹虚线（见 [`evidence/01_difference-vs-raw`](evidence/01_difference-vs-raw/)）；
4. **转录只看差分图，判分只收文本**。

**结构上的三道闸**（差分图输入与判分只收文本是代码与输入约束，不是统计结论）：

1. **差分图输入**：转录输入用差分图而不是原图，印刷题干在输入阶段就不存在；
2. **抹残留虚线**：差分后仍残留的印刷虚线也要抹掉（`99.6%` 那一路），因为残留线条同样会提供可借用的上下文；
3. **判分只收文本**：判分阶段只接收转录文本，`services/flash_grading.py` 对 `text` 阶段显式拒绝任何图片输入，判分模型看不到原始笔迹。

这条结论决定了架构顺序：教师确认模板 → 差分只剩笔迹 → 转录只看笔迹 → 判分只接收文本（`text` 阶段显式拒绝图片）。**就算将来模型不再被题干带偏，差分仍然划算**：模型不用读题干，也不用把题干再抄一遍，速度和 token 都省在这一步（数字见[最终效果](#5-最终效果)）。

#### B. 按题分片与跨页尾块

![按题分片与跨页尾块：每路请求带整页原图和各题粗定位裁图，只负责自己的题；接上页的题额外带上一页尾块](docs/readme-assets/cross-page-tiling.svg)

这一段的解题与转录对象是**模板本身**：替教师解出每道题的标准答案、录下印刷题干，所以必须看到完整题干；差分去题干针对的是学生卷转录，两者不矛盾。

- **按题分片**：Max 解题按 Flash 题号目录拆成并行分片（`OCR_TEMPLATE_SOLVER_SHARDS`，默认 2 路；实际路数不超过题组数，也不超过 Max 在途上限减去定位占用）。同一印刷大题的小问归为一组不拆开，每题恰好一个负责分片，分配在任何 Max 调用之前定死，合并时不需要在两份答案之间取舍。每路带同一组图——第 1 张是整页原图，后面是各题的粗定位裁图——和同一段解题提示，只在末尾追加「本请求只负责以下题目」，各路因此共享可缓存的前缀；每路只输出自己负责的题，整页的长解答不再挤进同一个请求。转录是一路请求，带同一组图。
- **跨页尾块**：本页第一道题没有印刷题号、被目录标为「接上页」时，导入流程把上一页的矫正图和识别结果交给这一页，从上一页最后一题的题号框上沿裁到页底，横向取该题所在那一栏，上、左、右各留 1.5% 余量，高度不小于页高的 10%。这张尾块只追加给负责该题的那一路解题请求和转录请求，作为最后一张图；目录行同时说明题干是最后一张图中的最后一道题，两处都没有的已知条件不得自行补设。其余请求与没有上一页时逐项相同，不新增请求。
- **退路与把关**：最后一题不在最后一栏（可能折到下一栏）或上一页没有识别结果时，改带上一页整页；上一页的图读不出时，本页照原样识别。接上页的题仍固定转教师复核，原因写明「标准答案由上一页的题干与本页内容共同得出，请对照上一页核对」。只在「答题页接在印有题目的页之后」时才找上一页：答题卡的题干在试题册里、封面上没有题目，都不找。
- **实现与测试**：`services/template_solver_shards.py`、`services/template_cross_page.py`；`tests/test_template_solver_shards.py`（270 行，12 个测试函数）、`tests/test_template_cross_page.py`（449 行，15 个测试函数）。

### 5. 最终效果

回到开头那个场景：同样 30 张卷子的量，当时约 50 分钟且误判频出；现在用当前链路，有把握 15 分钟内批完，且「改答案」型误判被三道闸（差分图输入 / 抹残留虚线 / 判分只收文本）压住。成本随批阅量变化，口径见成本一节：一次整班批阅（两页模板 + 50 名学生）约 166 Credits。当初的两个目标——课后作业批改已是日常主链，错题整理落在题库、待入库答案与原题订正卷上。

#### 已核定数字

`evidence/` 里是可复算的原始数据（脱敏输入、模型原始回执、对照表、复算方法），不是宣传截图。

| 指标 | 原图 | 差分 | 差分 + 抹虚线 | 出处 |
|---|---|---|---|---|

| 转录准确率（25 道题、每题 10 次） | 243/250 = 97.2%（不使用模板差分的基线） | 245/250 = 98.0% | 249/250 = **99.6%**（原型实测；生产已上线同类处理） | [`evidence/01`](evidence/01_difference-vs-raw/) |
| 改答案型错误（生产提示词，每路 10 次） | 6/10 | **0/10** | **0/10** | `evidence/01` |
| 平均输出长度 / 耗时（同一句裸提示词，50 次） | 2556 字符 / 21.5 秒 | 468 字符 / 5.0 秒 | — | `evidence/03` |
| 中位数（同上） | 2302 字符 / 20.2 秒 | 501 字符 / 4.3 秒 | — | `evidence/03` |
| 平均耗时（生产提示词，01 的汇总均值） | 18.6 秒 | 8.2 秒 | — | `evidence/01` |

- **速度与输出**：同一句「转录这份试卷。」，输出短约 5.5 倍，耗时约 4.3 倍（50 次的中位数口径一致）；换成生产提示词也是 18.6 秒 → 8.2 秒（2.3 倍）。
- **显著性与置信上限**：同一句提示词，原图 50 次无一如实、差分 50 次全部如实，差距是显著的（Fisher 单侧 p≈1×10⁻²⁹）；但样本只有单卷单题，0/50 的 95% 置信上限约 5.8%（连同 01 的两路差分合计 0/70，上限约 4.2%），只能说「这道题上没再出现」，不能外推成「不会再发生」。
- **结论口径**：提示词只改变概率，试过的 3 种提示词都没压到 0，差分掉题干是这组实验里唯一做到 0 的改动。
- **这些数据显示**（单卷、每路 10 次）：模板差分减少了印刷体残影对转录的干扰，「把题目里的 A 抄成 B」这类会改变答案的错误在差分两路 20 次中为 0；判断题号与作答位之后，手写漏符号时判分仍给出 37 correct / 5 partial / 0 wrong，且没有把读错的作答判成正确（[`evidence/02_handwriting-robustness`](evidence/02_handwriting-robustness/)）。

每次调用的 token 用量（供应商回报值，不是估算）在 [`evidence/04_usage-cost`](evidence/04_usage-cost/)；价格随供应商、区域、缓存命中率变，仓库不写死——读者按自己拿到的价目表代入 `compute.py`。用阿里云 Token Plan 订阅的走 [`token-plan.md`](evidence/04_usage-cost/token-plan.md)，那里是 Credits 口径：按当前实测用量，一次整班批阅（两页模板 + 50 名学生）约 166 Credits；按量价 ¥1.6–2.2、按 ¥139 档折合约 ¥0.5。

## 能力与边界

> 当前行为以源码、`config.py`、测试和实际运行回执为准。

- 详细批阅：模板/版面确认、身份门控、OCR、判分、复核、归档与报告。
- 模板链路：单栏、双栏、三栏处理；教师确认后的题目、作答位和几何才可进入学生批阅。
- 教学与学情：班级管理与风险分组、成绩报告、家长信专属链接、题库与待入库答案、出题练习与原题订正卷、课件库、教师助手（见总览第 6 节）。
- 识图办公：`/api/vision-office`，在配置完整时由教师助手读取模板并生成办公文件。
- 可选桌面节点：只做图像预处理；模型凭据、最终校验和成绩写入仍在服务器。

边界：

- 答题卡路由已注册，但 `ANSWER_SHEET_GRADING_ENABLED` 默认关闭；未完成真实学生答题卡验收前，不把它当作默认生产主链。
- 核心批阅链路只装 `requirements.txt`。教师的「办公助手」是可选组件，装在 `requirements-optional.txt` 里 —— 它把 certifi/PyJWT 钉在旧版本，和核心依赖互斥，两个文件不能一起装。
- 跨页续题的上下文截断是「已知问题 + 针对性缓解」，没有完全解决（见[如何思考的](#3-如何思考的)）。

## 部署与运维

**产品定位：一台服务器 = 一个学校，设计寿命三年**（三年到期后整体清理历史数据）。**硬约束：单实例部署** —— 不要并行运行第二个应用容器，不要 `--scale`。SQLite（`data/mathagent.db`）是唯一事实源，学生卷图片在 `uploads/`，两者都是本机磁盘。

- **模型密钥加密存储**：模型密钥在库里是 AES-GCM 加密存储（`enc:v1:` 前缀），主密钥来自环境变量 `MODEL_KEY_MASTER` 或首次启动生成的 `data/.model_key_master`。**备份 `data/` 时必须连 `.model_key_master` 一起备份**，否则已保存的 Key 无法解密，需要在设置页重新填写。
- **首次启动初始密码**：管理员初始密码在 `docker compose logs app` 首次启动时打印，同时以 0600 权限写入 `data/.first-run-password`；登录后请立即改密。忘记密码时用 `docker compose exec app python scripts/set_admin_pwd.py` 显式重置：启动流程只在「没有管理员」或「管理员没有密码」时写入初始密码，已有密码**不会**被 `.env` 的 `ADMIN_PASSWORD` 覆盖——所以改 .env 等它自动还原是无效的。
- **短信登录默认关闭**：默认 `SMS_ENABLED=0`，登录页只保留密码登录，没有阿里云短信账号也能用。
- **Redis 只存易失状态**（限流计数、进行中的租约），不是数据源。Redis 数据全丢只影响进行中的操作，不影响成绩与档案。
- **备份范围**：`data/`（含 `.model_key_master`）与 `uploads/` 必须一起备份；`redis-data/` 只存易失状态，可以随时丢弃。
- **手动部署（进阶）**：不使用容器时走原有的 systemd + nginx + venv 流程：见 [`deploy/README.txt`](deploy/README.txt)、[`deploy/setup.sh`](deploy/setup.sh) 与 [`deploy/mathagent.service`](deploy/mathagent.service)。发布前先运行 `bash deploy.sh --dry-run`，真实部署与服务重启须单独授权。

<details>
<summary><b>Docker 部署（推荐）完整步骤</b>：启动、首次启动、教师账号与批阅密钥、worker、备份与恢复、改配置</summary>

```bash
git clone https://github.com/liwangcc/mathagent && cd mathagent
docker compose up -d --build
# 浏览器打开 http://<服务器IP>:8080
```

`ALLOWED_HOSTS` 默认是 `*`，所以按 IP 直访就能打开；配了域名就在 `data/.env` 里写 `ALLOWED_HOSTS=math.example.com`，否则 Host 校验会返回 400。

首次启动会自动完成三件事：建库、生成 `JWT_SECRET`（写入 `data/jwt_secret`，之后重启沿用，不会重新生成把所有人踢下线）、生成管理员初始密码（见上方「首次启动初始密码」）。

- **教师账号**：管理员登录后到「系统设置 → 教师账号」给老师建号（手机号可留空，系统会生成一个 199 开头的登录账号），把「登录账号 + 初始密码」交给老师即可。
- **批阅密钥**：登录后到「系统设置 → 模型密钥」，简单模式只填两个槽——「模板定位与解题」和「学生卷转录与批阅」；展开专家模式才需要分三个职责组单独配置。每个职责只用一把密钥：同一厂商按出口 IP 限流，多把同厂商密钥共享同一配额，要提速请向厂商申请更高并发配额。
- **worker 数**：容器内 `GUNICORN_WORKERS` 固定为 1 或 2。验证码票据与微信 OAuth state 只存在 `data/auth_tickets.db`（SQLite，同机所有 worker 共用一个文件）；登出黑名单与限流计数在 Redis / SQLite 共享存储里。两个 worker 不会出现「A 签发、B 校验失败」。
- **备份**：建议先停应用再打包，避免拷到写了一半的 SQLite 文件：

  ```bash
  docker compose stop app
  tar czf mathagent-backup-$(date +%F).tar.gz data uploads
  docker compose start app
  ```

- **恢复**：解压回原目录后启动即可。`data/.model_key_master` 丢失时，已保存的模型密钥无法解密，需要到设置页重新填写——这也是它必须跟库一起备份的原因。
- **改配置**：想改端口、开短信、配微信登录时，把变量写进 `data/.env`（容器启动时会读取，格式为简单的 `KEY=VALUE`），再 `docker compose up -d`。

</details>

## 本地开发与验证

准备 Python 3.11+、Node.js 18+。真实密钥只放本地 `.env` 或受保护部署环境，不提交 Git。核心批阅链路只装 `requirements.txt`（可选的办公助手依赖与核心互斥，见[能力与边界](#能力与边界)）。

```bash
# Python 环境（已有 venv_local 时跳过创建）
python -m venv venv_local
./venv_local/Scripts/python.exe -m pip install -r requirements.txt

# 前端依赖与开发服务器
cd frontend
npm install
npm run dev

# 另开终端启动后端
./venv_local/Scripts/python.exe app.py
```

验证：

```bash
# 一次性装好开发依赖（含 pytest 与 pytest-asyncio）
venv_local/Scripts/pip install -r requirements-dev.txt   # Windows
venv_local/bin/pip install -r requirements-dev.txt       # Linux / macOS

# 仓库根目录
env -u PYTHONPATH ./venv_local/Scripts/python.exe -m pytest -q

# frontend/
npm run test
npm run build
```

部署前先运行 `bash deploy.sh --dry-run`。真实部署、生产配置/数据库变更和服务重启须单独授权；健康检查或单元测试通过不等于真实教师浏览器流程通过。
