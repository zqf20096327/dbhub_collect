# 让事务引擎以为自己在写本地文件——PALF 把 Paxos 做进 WAL，而不是把数据库塞进状态机


把共识协议接进数据库，通常的做法是复制状态机（RSM）：数据库是状态机，日志是命令流，每个副本重放命令流把自己推到同一个状态。PALF 反过来做——事务引擎用一套 append-only 的文件式接口写日志，共识协议藏在这套接口背后，对数据库不可见。

代价是日志系统要补回"本地文件"本该有、而复制日志默认给不了的几样东西；换来的是：单个复制组在 8000 客户端下做到 148 万次 append/秒，装进 OceanBase 跑三副本，相比单机只多 8.8% 的开销。

PALF（Paxos-backed Append-only Log File System）出自 OceanBase 团队，发表于 PVLDB 2024，是 OceanBase 4.0 底下的复制 WAL 层，已用于生产，源码在 OceanBase 开源仓库的 `logservice/palf`。这篇文章只讲一件事：把共识做进 WAL 模型、而不是 RSM 模型，会怎样改变一套复制日志的设计。先从这两个模型的区别说起。

## 问题背景：RSM 模型为什么不适合数据库

复制状态机模型是大多数系统接共识的方式：客户端提交一个"打算做的操作"，系统据此生成日志，共识协议把日志复制到多数派，每个副本再把日志里的操作重放（apply）到自己的状态机上。给 KV 存储设一个键值，这个模型干得很好——操作小，日志小，重放快。

数据涉及量一大，它就有两个坎。第一个是大事务得先攒起来。状态机要先拿到完整的操作才能生成日志，所以数据库需要额外的缓冲区，把客户端发来的临时数据缓存下来用于生成日志；一旦事务大于这个缓存就难办。折中办法是限制事务大小、把大事务拆成小的操作单元——代价是丢掉了用户原本那个事务的原子性。第二个是事务内的读看不到自己刚写的。写还没 apply 到数据库，事务里的后续读就读不到前面的写；要读就得去缓存里读，再和存储引擎里的数据合并，多一层开销，读性能下降。

两个坎是同一件事的两面：在 RSM 模型里，日志是状态机要重放的命令流，数据库只有在 apply 之后才"成真"，所以数据库不得不把所有未完成的东西都堆在日志前面那一层。

PALF 的选择是把共识接进 WAL 模型。WAL 模型里，数据库用本地文件系统的接口写日志，**记日志和应用操作的先后顺序和 RSM 正好相反**：写直接落到内存里的存储引擎（也就是状态机本身），然后才生成 redo 日志、flush 到 PALF。事务引擎把 PALF 当一个本地日志文件，只关心日志记录刷下去了没有。这一反转带来两个直接后果：事务大小的上限被放开，只受存储引擎容量限制，不再受日志生成缓存限制；读请求直接访问存储引擎，不必再去缓存里捞、再合并。

换句话说，"大事务不受限"这条线，MaLT 是在存储引擎那一层用 LSM-tree 内嵌事务做到的，PALF 是在日志这一层、靠换掉日志模型做到的。但把日志当本地文件用、这个文件又得跨机器复制时，本地文件本来的那些保证就不再自动成立。

## PALF 在 OceanBase 里的位置

先看 PALF 在数据库里站在哪。

OceanBase 1.0 到 3.0，事务、日志、数据存储的基本单位都是表的**分区（partition）**。随着用 OceanBase 的中小企业变多，这套架构暴露出两个问题：一台机器上有几万个分区，就有几万个 Paxos 组，光维持这些复制组就吃掉可观的资源，抬高了部署和运维的门槛；另一个是大事务——一笔事务可能横跨几万个分区，于是一笔事务的两阶段提交可能有几万个参与者，协调开销随参与者数上升，把系统推向不稳定。

OceanBase 4.0 重新设计，引入了一个叫**日志流（Stream）**的组件。一个日志流 = 一组数据分区 + 一套复制 WAL + 一个事务引擎。关键变化是：表还是按分区切的，但事务和日志的基本单位从"单个分区"变成了"一个日志流里的一组分区"。事务引擎把这组分区的改动生成 redo 日志，写进这个日志流的 WAL。**复制组的数量因此从"每分区一个"降到了"每服务器一个"。** 每台服务器上有一个日志流，它的 leader 就选在这台服务器上；多台服务器上不同日志流的 leader 同时对外服务，构成一个 active-active 的架构。单机模式下它的性能接近集中式数据库，加机器就能扩展。

PALF 本身分三层。最上面是接口层，对外暴露文件式接口，并负责协调 PALF 副本和事务引擎的角色。中间是副本层，每个 PALF 组有多个副本分散在不同服务器上，里面是 log sequencer（分配日志序号）、Paxos 内核、选举、重配置这几块。最下面是每台服务器一个的运行时环境 PALFEnv：日志以定长块的形式存在 LogStorage 里，成员等元信息存在 MetaStorage 里，BlockGC 回收不再需要的块，所有 I/O 走一个统一的 I/O worker。

对外的数据接口就这么几个，数据库像用文件一样用它们：

| 接口 | 作用 |
|---|---|
| `append(r)` | 把记录 `r` 追加到 leader，返回它的 LSN。**异步**：返回只保证日志拿到了 LSN、进了 leader 的缓冲；是否提交由回调 `AppendCb` 通知——多数派持久化了走 `success`，否则走 `failure`，每条至多回一次。 |
| `mirror(lsn, l)` | 另一种写入：只接受另一个 PALF 组已提交的日志，用于做镜像（见后文数据同步）。同一时刻一个组只能被 `append` 或 `mirror` 之一写入。 |
| `read(lsn)` | 按 LSN 随机读日志。 |
| `locate(csn)` | 把一个变更序号映射到 LSN。 |
| `monitor_tail` / `monitor_role` | 注册回调，监听日志尾的推进、以及副本角色的切换（leader↔follower）。 |
| `trim(lsn)` | 标记某 LSN 之前的日志无用，交给 BlockGC 回收。 |

这张表就是 PALF 想划的那条边界：数据库特有的需求，统统收敛成几个接口。`append` 返回 LSN、`AppendCb` 回显式结果、`locate` 接受变更序号——这几个看似普通的签名背后，正是下面要补的几样东西。

## 当日志变成"会复制的本地文件"，有四件事要补回来

本地文件给你两个保证：每次 write 都返回明确的成功或失败；文件放在哪台机器，是你说了算。一套跨机器复制的日志，这两个默认都给不了——共识协议在异常时往往不告诉你那条日志到底成没成，leader 选在哪台机器由协议内部决定。要让数据库真把它当本地文件用，PALF 得补四样东西：

1. **可控的选主**：leader 的位置要由数据库的意愿决定，而不是由"谁的日志最新"决定。
2. **显式的复制结果**：哪怕发生异常，也要明确告诉事务引擎某条日志是提交了还是被丢弃了，否则事务会卡住。
3. **跨组定序**：LSN 只在单个组内有序，跨组的事务之间定不了先后。
4. **跨集群的数据同步**：备库、恢复库要靠同步日志来建，而且彼此要能独立运维。

下面逐个看，以及为此各付了什么代价——其中前两样（可控选主和显式结果）是同一条因果链上的两环，放在一起讲。补完这四样还剩最后一笔账：把复制组降到每服务器一个，海量 redo 就全压在单个 PALF 组上，单组必须足够快——这笔账放在最后单独还。

## 选主与显式复制结果

leader 选在哪，几乎影响所有功能：故障恢复、日常运维、让 leader 靠近上层应用以降延迟。传统上选主是共识协议内部的事。Raft 有一个 leadership transfer 扩展，但它只在新旧 leader 都活着时管用；一旦旧 leader 崩了，谁能当选完全由它存的日志决定，而不是用户的意愿。要是选出来的副本不是你想要的，就得靠一个外部协调者去检测失败、再执行转移——协调者自己再崩，可用性又多一个风险点。

PALF 把选主从共识协议里拆出来。用户给副本指定**选举优先级**，选主算法保证"在多数派里优先级最高"的副本当选。旧 leader 崩了，次高优先级的副本直接顶上，不需要任何外部操作；旧 leader 恢复、且优先级仍然最高，leadership 会自动转回去。选主本身用一个基于租约的算法（Basic Paxos 的变体，对"谁在多数派里优先级最高"达成共识），保证同一时刻不会选出两个 candidate；算法细节论文留给了另一篇。

把选主从共识里拆出来是有代价的：选举只看优先级，当选的 candidate 日志可能比别的副本短。所以它正式当 leader 之前，要先做一遍 **log reconfirmation**（论文里的 Algorithm 1，本质是一次完整的 Basic Paxos）：candidate 拿着比当前更大的 ProposalID 广播 Prepare，每个副本只在这个 ProposalID 比自己见过的都大时才回应——而且只回自己日志尾的 LSN，不回整段日志，省传输。收齐多数派的回应后进入 accept 阶段：挑日志最长的那个副本，把它的日志取过来、复制给所有副本；最后再复制一条 StartWorking 日志（一种特殊的重配置日志，用来回滚前任 leader 可能没提交完的成员变更），这条日志到了多数派，candidate 才正式开始干活。这一步保证了新 leader 的日志不短于多数派里的任何副本，对应 Raft 里的 election safety 和 leader completeness。

于是一个副本有四种角色：follower、candidate、pending follower、leader。启动时是 follower；周期性地问选举算法"candidate 是不是我自己"，是就转 candidate、做完 reconfirmation 再转 leader。而一个 leader 发现 candidate 不再是自己、或者收到了 ProposalID 更高的新 leader 的消息，就得让位——但它不是直接转回 follower，而是先转成 **pending follower**。

![图 f3 · 四角色状态机：让位的旧 leader 先进 pending follower，等账算清才转 follower](figures/f3.png)

为什么要多一个 pending follower，正是"显式复制结果"这件事的核心。在 WAL 模型里，一笔事务该提交还是该回滚，取决于它的 commit record 有没有被多数派持久化。当一个 leader 因为网络抖动让出 leadership 时，它之前 append 的一些日志（pending logs）结果是未知的——本地文件会明确告诉你 write 成没成，但多数共识实现在这种异常下不回显式结果，事务引擎就卡在那里不知道该提交还是回滚。

PALF 的保证是：**除非 leader 崩溃、或者网络永久中断，事务引擎一定会被明确告知每条日志的复制结果。** 让位的旧 leader 转成 pending follower 后，等新 leader 的日志过来，那些 pending logs 的命运就变明确了：被新 leader 也提交了的，旧 leader 对数据库回 `success`；被截断的（同一位置上有 ProposalID 更高的另一条日志），回 `failure`。每条记录只触发一次回调，至多一次。等所有 pending log 都算清了账，副本才转成正常的 follower——这就是它要先停在 pending follower、而不是直接转 follower 的原因。

论文里的一个例子能把这条路径走完整：

![图 f4 · 显式复制结果：同一批 pending 日志，一条 success、一条 failure（框内数字 = append 时 leader 的 ProposalID）](figures/f4.png)

副本 A 原本是 leader，append 了 log1、log2、log3，但还没来得及复制出去就被网络分区隔离了。这期间 C 当选新 leader，从 B 那里 reconfirm 到了 log2。网络恢复后，A 因为租约过期转成 pending follower，开始接收新 leader C 的日志：log2 已经被新 leader 提交，A 对数据库回 `success`；log3 被截断了，因为 C 那边有一条 ProposalID 更大的 log3，A 对它回 `failure`。如果 A 不是让位、而是直接崩溃，PALF 根本不用通知数据库——内存里的状态全丢了，A 恢复后老老实实转 follower、重放本地日志把事务恢复出来即可。

这套机制保证的是共识里的 state machine safety：一条日志被提交，就一定 apply 到了 leader、并会重放到 follower；没能达成共识的日志，前任 leader 的状态机会被那次 `failure` 回滚掉。换句话说，WAL 模型要求日志系统对外回显式结果，pending follower 就是 PALF 为兑现这个要求加的那个角色。

## CSN：用一个号给跨组事务定序

下游的数据消费工具（比如 CDC）要按事务发生的顺序消费它们。但 LSN 干不了这个活——LSN 是日志在单个 PALF 组内的物理偏移，只在组内有序。为了扩展，数据分区散布在多个日志流里；两笔事务改的是不同日志流里的分区时，它们的 LSN 根本没法比。

一个自然的做法是把事务的 commit version（标记事务提交时刻的版本号，用于可见性判断）塞进日志的 payload 里，让下游去读。但有两个毛病：commit version 不一定随 LSN 严格递增（并行执行时，完全可能给一个 commit version 更大的事务分到更小的 LSN）；而且这逼着每个日志消费者都去解析 payload，多一层开销。

PALF 的办法是给每条日志再配一个标识符：**CSN（Change Sequence Number）**，一个 64-bit 整数，存在日志头里。PALF 不关心 CSN 是什么含义（所以维护它的成本极低），它只维护一条不变式：CSN 在一个组内单调递增，并且和 LSN 的顺序一致——

> 对同一个 PALF 组内的任意两条日志 α、β，若 `LSN_α ≥ LSN_β`，则 `CSN_α ≥ CSN_β`。

CSN 随日志一起持久化，所以即使 leader 崩了它依然有效。

![图 f5 · CSN 不变式：CSN 随 LSN 单调，且由 RefCSN 携带全局含义，于是能给跨组事务定序](figures/f5.png)

光是组内单调还不够，要跨组定序，得让 CSN 携带一个全局有意义的值。`append` 为此多了一对参数：入参 `RefCSN`、出参 `CSN`，保证 `CSN ≥ RefCSN`。`RefCSN` 是一个因果参考——它表示"这条日志一定排在 `RefCSN` 那个事件之后"。只要 `RefCSN` 填的是一个全局有意义的值，返回的 CSN 就能反映全局顺序。

OceanBase 正是用这个机制给事务做全局的 commit version：事务要提交时，从一个全局时间戳服务取一个时间戳当 `RefCSN`，把 commit record append 进去，`append` 返回的 CSN 就当这笔事务的 commit version。因为 CSN 可能比当前全局时间戳还大，一笔事务有可能对"取了更小可读版本的未来读请求"不可见；为避免这点，事务引擎会等到全局时间戳超过这笔事务的 CSN，才给客户端回提交成功。

follower read 顺带就成立了。让 follower 副本以最终一致的方式分担只读请求，需要保证：一个读版本 T 能在 follower 上读到完整数据，当且仅当所有 CSN 小于 T 的日志都已在该 follower 重放、且未来任何写的 commit version 都大于 T。CSN 的单调性天然给了这个保证——日志按 LSN（也就是 CSN 的顺序）复制并重放到 follower，一旦 CSN 为 T 的日志被重放，后面的日志 CSN 都比 T 大。别的分布式数据库要靠周期性广播特殊命令（比如 closed-timestamp）来推进 follower 上的可读时间戳，OceanBase 这里不需要额外机制。

## 数据同步：抽象成一个可独立重配置的镜像组

分布式数据库是数据流的源头，下游应用靠同步它的物理日志来提供各种服务。OceanBase 里有两个典型场景：**物理备库**和**数据库恢复**。物理备库是一个数据与主库完全一致的独立数据库，可以分担一部分读、在主库故障时 failover 顶上去当主库，提供的是数据库级的容灾；这和副本级的保护（比如 Paxos learner）不是一回事。数据库恢复则是把存在离线存储（NFS、对象存储）里的归档日志，重放成一个一模一样的库。

两件事的内核是同一个：把记录在物理日志里的数据变更，从一个 PALF 组（或外部存储）同步到另一个 PALF 组，而且这两个组要能各自独立地可用。一个想当然的做法是从主组读日志、当成记录 `append` 到备库对应的组里——但共识协议会给 `append` 进来的记录再加一个日志头去复制，结果主备两边的日志格式就不一致了。

PALF 把这个需求抽象成一个 primitive：**PALF group mirror**（镜像组）。它是一个独立的 PALF 组，跑同样的共识协议，维护着数据变更前缀的一份镜像，镜像的来源可以是主 PALF 组、也可以是外部存储。它能独立重配置，也能在需要时切换成一个主组。

主组和镜像组的区别只在写入来源：主组用 `append`，记录会被加上日志头再复制；镜像组只用 `mirror`，**只接受另一个主 PALF 组已经提交的日志**，并复用这些日志原本的 LSN 和 CSN，leader 把它们存到对应的 LSN、再复制给自己的 follower。一个组到底是主还是镜像，用 Primary / Mirror 两种 access mode（标记一个组当前是主、可 append，还是镜像、只 mirror 的模式位）区分，靠 failover/switchover 切换；而"原子地把新 access mode 广播给所有副本"本身又是一个共识问题，所以 PALF 为它实现了一个 basic Paxos，把 access mode 存在 MetaStorage 里。

![图 f6 · PALF group mirror：镜像组只 `mirror` 主组已提交的日志、复用其 LSN/CSN，并能独立重配置](figures/f6.png)

有了镜像组，数据同步的架构就很自然：备库里所有 PALF 组都是主库对应组的镜像，恢复库里所有组都是外部存储里数据变更的镜像。主组提交日志后，归档器从各组读出日志存进外部存储或直传备库；备库的恢复器收到日志，`mirror` 给镜像组的 leader；提交后，再重放给所有副本（包括 leader 副本）的事务引擎。有个细节值得一提：备库里的事务引擎走的是标准的 RSM 模型——所有副本都只是读日志、重放数据变更，事务引擎的角色永远是 follower，哪怕它底下的 PALF 副本是个 leader。

镜像组还有一个要求：能独立重配置。很多共识实现把重配置命令当普通日志来存、来复制；这套"内嵌"的做法对镜像组行不通——一来它逼着事务引擎去过滤掉那些和数据变更无关的重配置命令，二来镜像组的成员和主组本来就可以不同，得能独立改，而镜像组只收主组的日志，没法靠"写一条普通日志"来重配置自己。所以 PALF 把重配置日志单独存进 MetaStorage，和 LogStorage 分开。

把元数据单独存并不像听上去那么简单，弄不好会破坏共识的安全性。论文举了两个例子：

![图 f7 · 独立元数据可能引入的两个异常：丢失已提交日志、脑裂](figures/f7.png)

一个是**丢失已提交日志**：LSN 不大于 5 的日志都已被 leader A 提交，此时 A、D、E 有最新日志，而 B、C 落后；A 想把 D、E 移出集群，于是只把新成员关系复制给新成员里的副本——可那几条已提交的日志（3、4、5）还没被新成员（A、B、C）的任何多数派 flush 过，于是丢了。另一个是**脑裂**：连续做重配置，先用 F 换掉 E，结果 B 和 F 可以投给 A、而 C 和 E 投给 D，选出了 A、D 两个 leader。

PALF 加了两个约束堵住这两个口子。重配置时，leader 在下发新配置的同时附一条 **log barrier**（发配置那一刻 leader 的日志尾），每个 follower 在自己 flush 的日志没追上 barrier 之前，拒绝接受这个新配置——上面那个例子里，B、C 没把 3、4、5 接收完，就不会接受新配置，已提交日志也就丢不了。选主时，PALF 维护一个 **config version** 标记成员关系的版本，每次重配置就加一，并把它当作首要的选举优先级——于是 config version 更低的 D 不会被选成 leader，脑裂也就堵住了。把元数据从日志里拆出来确实多了这些约束，但换来的是：元信息对日志消费者不可见，镜像组能独立重配置。

## 性能：拿什么换来的

把复制组数降到"每服务器一个"，意味着事务引擎会把海量分区的海量 redo 日志全压到单个 PALF 组上——单组很容易成为瓶颈。所以这套设计能不能成立，取决于单个组够不够快。PALF 在写路径上做了三件事。

**流水线复制。** 多条日志的处理和复制在多核上并发推进。把多条日志的共识相关状态缓存在一个内存里的滑动窗口里，避免 CPU cache miss，于是不同日志的复制阶段可以重叠起来。

**自适应分组复制。** 共识协议每提交一条日志，至少要两个网络往返加一些 CPU；把多条日志打成一批一起走共识，是摊薄这个开销的常规手段，难点在批多大合适。PALF 的 `freeze` 操作把缓存的日志打包成一个 group log entry 一起复制，一个 group log 里有几条日志（group factor）取决于 `freeze` 多久做一次。它的自适应在于：并发低时按固定间隔（默认 1ms）`freeze`，并发高时按 I/O worker 的反馈 `freeze`。客户端并发不好直接测，PALF 用 group factor 当它的代理量——可以推出 group factor 正比于并发度、又正比于 PALF 占用的 CPU 核数，于是批大小的阈值由硬件资源定，不用人去手调。比起需要调参的批量算法，这套更简单、更可预测，适合生产。

**无锁写路径。** 并发一高，锁争用就会吃掉性能。写路径上主要是 log sequencer 和 group buffer 两块。log sequencer 顺序地给日志分配 LSN，做成无锁的：一个线程要 append 时，原子地把 LSN 尾读到一个临时变量、加上自己这条日志的大小、再用 CAS 写回 LSN 尾；CAS 因并发失败就重读、重试。拿到 LSN 之后，多个线程并发往 group buffer 里填日志——因为 LSN 既是日志在盘上的地址、也是它在 group buffer 里的偏移，每条日志预留的那段 buffer 互不重叠，group buffer 就不是一个争用资源，多线程往不同偏移填，没有锁开销。

这三件事换来的吞吐，论文在 3 台 32 核 2.5GHz Xeon、256GB 内存、10GbE 的机器上，拿两个开源 Raft 实现 etcd-raft 和 braft 做对照（一些工业级分布式数据库就建在它们之上），客户端和 leader 同机、直接 append：

![论文 Fig.9 · 不同客户端数与日志大小下的吞吐和延迟（PALF 随客户端数近线性扩展）](figures/paper-fig9.png)

单个 PALF 组在 1500 客户端下处理 47.8 万次 append/秒，8000 客户端下到 148 万/秒。客户端从 500 涨到 8000，PALF 的吞吐涨了 5.98 倍，而 etcd-raft 和 braft 分别只涨了 1.386 倍和 1.8 倍——两个 Raft 实现的共识仍然是一条一条处理日志的，吞吐上不去。延迟方面，客户端少于 1500 时约 2ms，8000 客户端下也只到约 4.8ms。LSN 和 CSN 的分配是写路径上一段必须串行的环节，论文专门量过会不会成瓶颈：log sequencer 在 1000 线程下能扛 588 万次请求/秒，远没到瓶颈。

自适应分组的效果可以单独看一张图：

![论文 Fig.10 · 日志聚合：低吞吐时跟随反馈式的低延迟，高并发时切到周期式拿吞吐](figures/paper-fig10.png)

吞吐低的时候，自适应策略跟随反馈式分组拿低延迟；并发上去后，它切到周期式分组拿吞吐，不必在两者间做静态取舍。

故障恢复这一路也量过：

![论文 Fig.11 · 故障恢复：leader 崩溃后短时间内由新 leader 接管，reconfirmation 中位约 32ms](figures/paper-fig11.png)

leader 崩溃后，吞吐短暂掉到零，新 leader 很快接管、达到和前任相当的吞吐。恢复时间由两段组成：选主和 log reconfirmation。选主时长主要受租约（默认 4 秒）支配；log reconfirmation 相比 Raft 多花一点时间，但它的中位数和 90 分位分别只有 32.2ms 和 32.5ms——前面那条选举约束保证了新 leader 的日志不会落后太多，reconfirmation 只需补很短一段日志，相对默认 4 秒的租约等待可以忽略。

## 放进 OceanBase 里

上面都是 PALF 单独跑闭环客户端的数字。真正要回答的是：把它装进数据库，日志复制到底拖了多少后腿。论文用 OceanBase 4.0 跑了 Sysbench（insert、update）、TPC-C（200 仓）、YCSB 批量插入（OceanBase 的 KV 模式），还采了生产集群的数据。基准测试在 3 台 96 核 2.5GHz Xeon 上，生产集群是 46 台阿里云 ECS r5.16xlarge。

![论文 Fig.12 · OceanBase 在不同负载下的表现（Sysbench / TPC-C / YCSB / 生产）](figures/paper-fig12.png)

结论是：相比单机，三副本的 OceanBase 性能平均只降了 8.8%（为公平起见，只有一个副本处理事务）。性能随客户端数提升；TPC-C 下降得稍多一点，因为它写事务占比更高——日志复制主要影响写事务，对读事务几乎没影响，所以 Sysbench 这种写密集负载随客户端数近线性扩展，瓶颈在 PALF 而 PALF 仍有余量；TPC-C 这种混合负载的瓶颈在数据库本身、不在日志复制。

把 PALF 在 OceanBase 内部的实际负载剖出来，数字离它自己的峰值还很远：

| 负载 | 日志大小 | 吞吐（append/s） | 响应时间 | IOPS |
|---|---|---|---|---|
| Insert | 499 B | 472,181 | 3312 µs | 1125 |
| Update | 433 B | 484,061 | 3111 µs | 1111 |
| TPC-C | 3386 B | 27,975 | 3878 µs | 1929 |
| YCSB | 1993 B | 41,481 | 2024 µs | 1090 |
| 生产 | 1060 B | 23,253 | 4752 µs | 1129 |

对照前面单跑时 512 字节日志下 140 万 append/秒的峰值，可以看出 PALF 的能力对 OceanBase 的写入需求是富余的——日志复制不是 OceanBase 的瓶颈。

## 局限与设计取舍

PALF 借用了 Raft 的日志复制，但为了服务数据库改了五处，每一处都是一笔取舍：状态机模型用的是 WAL 而非 RSM；选主看的是优先级和 config version、并为此加了 log reconfirmation，而不是 Raft 那样"日志最新者当选"；让位时多了一个 pending follower 阶段来给 pending 日志定结果；重配置命令被拆成独立的元数据条目，而不是普通日志；日志标识用了 LSN 和 CSN 两个，而不是单一的连续索引。这些改动让 PALF 更贴合数据库，但也让它比一个教科书式的 Raft 复杂。

做物理备库时，为什么用镜像组而不用 Paxos learner，也是一笔权衡。两个原因：一是 failover——主库崩了，备库要能切成主库对外服务，而 learner 不是 Paxos 成员，很难被选成新主库的 leader；镜像组是独立的 Paxos 组，改个 access mode 就切过去了。二是可维护性——重配置通常由 leader 执行，如果备库依赖 learner，重配置它就得去联系主库，主备之间网络一断就卡住；镜像组能独立重配置，主库就算崩了，管理员照样能重配置备库。代价就是前面那套独立元数据带来的额外约束（log barrier 和 config version）。

还有一个贯穿全文的取舍：把多个分区的 redo 压到单个组上，好处是减少了分布式事务，代价是单个组必须足够快——上面那三个性能优化，正是为了还这笔账。选主算法本身的细节，论文没有展开，留给了另一篇。

把这些放在一起看，PALF 自始至终只做了一件事：把共识做进 WAL 模型，让数据库像写一个会自动复制的本地文件那样写日志，再把数据库特有的需求——显式的复制结果、跨组的定序、跨集群的数据同步——抽象成几个 primitive，在日志系统和数据库之间划出一条清晰的边界。它已经用在 OceanBase 4.0 的生产环境里，源码在 OceanBase 的开源仓库。
