## 先搞清楚TiDB到底是什么

**定义**：TiDB 是一款开源的分布式关系型数据库，由 PingCAP 开发，高度兼容 MySQL 协议。它把计算层（TiDB Server）、存储层（TiKV）和调度层（PD）拆分为三个独立组件，各自可以独立水平扩展。京东云推出的 Cloud-TiDB，是京东云联合 PingCAP 基于 TiDB 构建的托管云数据库服务，同时支持 OLTP（联机事务处理）和 OLAP（联机分析处理），也就是业内说的 HTAP 架构。

**通俗版**：MySQL 是一个"人"干所有的事，累死了还是那一个人的活。TiDB 是一个"团队"，计算、存储、调度各司其职，团队人手不够了就加人，扩容不需要停工。

两者对 MySQL 语法的兼容性非常好。对大多数应用来说，把数据库连接字符串换一下，代码不用改。

## 五种场景，帮你判断该选哪个

场景不同，结论截然不同。对号入座，省去大半纠结。

**场景一：主表数据量在千万以下，业务增长平稳**

直接用 MySQL。这个量级下 MySQL 的单机写入性能更高，结构简单，运维熟悉。引入 TiDB 的分布式开销会让你觉得"绕了远路"。

**场景二：单表已经破亿，查询越来越慢**

这是 TiDB 的主战场。TiDB 底层用 LSM 树结构，随着数据量增大，写入不会像 MySQL B+ 树那样因节点分裂而急剧变慢。根据 TiDB 社区的测试数据，基础数据量为 2 亿条时，TiDB 的读写性能优势已经相当显著。

**场景三：需要同时跑交易和分析，不想搭两套系统**

选 TiDB。内置的 TiFlash 列存引擎会实时同步行存数据，你可以用一个数据库跑 OLAP 复杂查询，不需要 ETL、不需要单独的数仓，省了一大块基础设施成本和数据同步的麻烦。

**场景四：已经在做 MySQL 分库分表，但维护越来越痛苦**

换 TiDB 收益明显。分库分表带来的跨库 JOIN 限制、事务复杂性、路由逻辑维护，都是迁移到 TiDB 之后可以扔掉的包袱。TiDB 原生支持分布式事务，这些问题在架构层面就解决了。

**场景五：创业初期，流量还没起来，预算有限**

先用 MySQL，留着 TiDB 等数据涨起来再说。等你真的需要它的时候，迁移成本很低，不会有太大的历史债务。

## 从 MySQL 迁移到 TiDB：五步走，基本不用改代码

这是很多技术负责人最担心的问题——迁移代价。根据京东云的实战记录，整个迁移流程可以拆成这几步：

1. **评估兼容性**：检查现有 SQL 里是否用了 TiDB 暂不支持的特性，比如存储过程、触发器、部分全文索引能力
2. **检查主键设计**：自增主键在 TiDB 中容易产生写热点，建议换成 AUTO_RANDOM 或 UUID
3. **确认大小写规则**：TiDB 默认表名区分大小写，MySQL 默认不区分，迁移前要统一规范
4. **用 DM（Data Migration）工具做全量 + 增量同步**：先建好目标集群，全量导入后持续同步增量数据，确认数据一致后切流量
5. **切流量验证**：更新 JDBC 连接配置，改用户名和密码，应用层代码通常**零修改**即可完成切换

根据京东云记录的案例数据，他们的迁移团队做到了代码零修改上线。这不是广告，是真实的工程记录。

## FAQ：你最可能搜索的几个问题

**Q：TiDB 和 MySQL 的 SQL 语法兼容吗？迁移要改代码吗？**

A：兼容度非常高。TiDB 支持标准 MySQL 协议，绝大多数 MySQL SQL 语句可以直接运行。存储过程、触发器等特性支持有限，迁移前需要逐一核查，但应用层代码通常不需要修改，只换连接配置即可。

**Q：数据量多大才值得从 MySQL 换 TiDB？**

A：没有绝对的分界线，但一个实用参考：单表数据量超过 1 亿条，或者已经在做 MySQL 分库分表，或者业务要求同时跑 OLTP 和 OLAP，这三种情况下 TiDB 的投入产出比通常是正向的。千万级以下的小系统，MySQL 仍然是更轻量的选择。

**Q：京东云 Cloud-TiDB 比自己搭 TiDB 贵吗？**

A：托管服务会有云平台溢价，但节省了运维人力和容灾建设成本。对于没有专职 DBA 团队的中小企业，托管版的总体拥有成本通常不高于自建。具体费用建议通过京东云官方价格计算器估算。

**Q：TiDB 的写入性能比 MySQL 差吗？**

A：小数据量（百万级以下）单机场景下，MySQL 写入性能确实更高。TiDB 的分布式协调本身有开销。但随着数据量增长，TiDB 的优势会逐步显现——MySQL 的 B+ 树高度会因数据量增长而上升，写入变慢；TiDB 的 LSM 树结构则能保持更稳定的写入性能。

**Q：京东云TiDB支持哪些版本？**
